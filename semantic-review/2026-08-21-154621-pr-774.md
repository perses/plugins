# Regex color overrides for BarChart

Adds a `visual.colorOverrides` list to the BarChart spec so dashboard authors can pin a color to series or bars whose name matches a regex, falling back to the theme palette when nothing matches. The runtime resolves overrides through a new `getOverrideColor` helper, called once per series in the grouped/stacked path and once per bar (via an ECharts `itemStyle.color` callback) in the ungrouped path. The editor gains a "Color Overrides" group with add/remove rows, a regex text field, and the shared `OptionsColorPicker`. First match wins; empty and invalid patterns are skipped rather than throwing.

Watch for: the Go SDK and `docs/barchart/model.md` were not updated, so the new spec field is unreachable from Dashboard-as-Code and undocumented (confirmed); the new `visual` block is an inline CUE struct rather than a closed definition, so typos like `colorOverides` and arbitrary extra fields validate successfully (confirmed by `cue vet`); the `{regex, color}` shape duplicates, with weaker validation, the regex-conditional coloring contract the Table plugin already persists as `cellSettings` + `#condition` (confirmed); and the ungrouped palette lookup was rewritten to `palette?.[0] ?? ''`, which paints an invalid color instead of deferring to ECharts if a theme ever ships without `color` (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The feature shape is the main design question. This repo already has a persisted contract for regex-driven conditional coloring in the Table plugin: a kinded `#condition` union (`Value`/`Range`/`Regex`/`Misc`) with `strings.MinRunes(1)` on the expression and hex-validated color fields. BarChart introduces a second, flatter, unvalidated shape. Once dashboards persist `visual.colorOverrides`, the field name and shape become a compatibility commitment, so the divergence is cheaper to settle now than later.

Schema strictness is weaker than every sibling plugin. `spec` is `close({...})`, but the nested `visual` struct is inline rather than a `#visual` definition, and CUE only closes the outer struct. `regex` accepts the empty string that the editor's Add button creates, and `color` accepts any string where timeserieschart and table both constrain hex.

The change is TypeScript-and-CUE only. `barchart/sdk/go/bar.go` has no `Visual`/`ColorOverrides` field, `docs/barchart/model.md` still lists the spec without `visual`, and `docs/barchart/go-sdk.md` has no matching option, leaving the plugin's representations out of sync with the contributor rules.

Runtime wiring is asymmetric by necessity: grouped/stacked series get a single `itemStyle.color`, ungrouped bars get a per-item callback keyed on `params.name`. That callback also replaced a broken palette lookup (`echartsTheme[0]`, always undefined) with an explicit `palette?.[0] ?? ''`, converting a silent ECharts fallback into a hardcoded index-0 read with an invalid-color escape hatch. It recompiles every regex for every bar on every render, and the patterns come from the dashboard spec, so a catastrophic-backtracking pattern runs in the viewer's tab.

The editor accepts patterns that silently do nothing: an empty regex on add, and invalid regexes as they are typed, with no error state on the field. Tests cover `getOverrideColor` and editor add/remove, but not the edit handlers, the reset path, or the chart wiring itself.

### Two conventions for regex-driven coloring

Table already persists this exact capability:

```cue
#regexCondition: { kind: "Regex", spec: { expr: strings.MinRunes(1) } }
#cellSettings: {
	condition:        #condition
	textColor?:       =~"^#(?:[0-9a-fA-F]{3}){1,2}$"
	backgroundColor?: =~"^#(?:[0-9a-fA-F]{3}){1,2}$"
}
```

Its matcher (`table/src/models/table-model.ts:221`) is the same three lines as the new `getOverrideColor`: compile, `test`, swallow failures, treat empty as no match. BarChart instead persists `[{regex, color}]` with no constraints on either field. Two shapes for one concept means Dashboard-as-Code users, migration authors, and any future override UI have to learn both, and the kinded union is what buys extensibility: the thresholds-plus-color precedence question already raised in review is easier to answer when an override carries a `condition` kind than a bare `regex` string.

### Open nested struct in bar.cue

`spec: close({...})` closes only the top level. The new `visual` is an inline struct, so it stays open:

```
$ cue vet ./schemas/bar.cue typo.json     # visual.colorOverides + visual.bogusField
$ echo $?
0
```

The same probe against timeserieschart, where `visual?: #visual` points at a definition, fails with `spec.visual.bogus: field not allowed`. A misspelled override key therefore ships as a valid dashboard that silently applies no colors. Every sibling plugin with a `visual` block (`timeserieschart`, `tracetable`, `tracingganttchart`) uses a definition.

### Palette fallback rewrite in the ungrouped path

The old ungrouped code read `color: chartsTheme.echartsTheme[0]`, which is `undefined` for an `EChartsOption`-shaped theme, so ECharts fell back to its own palette. The new callback makes the palette read explicit:

```ts
color: (params: { name: string }): string => {
  const overrideColor = getOverrideColor(params.name, colorOverrides);
  if (overrideColor) return overrideColor;
  const palette = chartsTheme.echartsTheme.color as string[] | undefined;
  return palette?.[0] ?? '';
}
```

Two things shifted. The cast asserts `string[]` on a field ECharts types more loosely, and the `?? ''` branch hands ECharts an invalid color instead of letting it fall back. Returning `undefined` with a `string | undefined` return type preserves the previous behavior exactly and removes the empty-string sentinel.

An empty `color` in a persisted override is swallowed rather than validated: `overrideColor ? { color: overrideColor } : {}` treats `''` as no match, while the editor renders `override.color || '#555'`, so the swatch shows grey while the chart draws palette color.

### Regex work inside the render path

`getOverrideColor` compiles each pattern with `new RegExp` on every call. In the grouped path that is bounded by series count, but the ungrouped path runs it inside the ECharts `itemStyle.color` callback, which fires per data item on every render, so cost scales with bars × overrides × renders and invalid patterns are re-thrown and re-caught each time. Compiling once per `colorOverrides` change in a `useMemo` and passing the compiled matchers keeps the same semantics.

The patterns come from the dashboard spec, which the viewer may not have authored, and they execute in the viewer's browser against every series name. A pattern like `(a+)+$` is enough to hang the tab. Low severity next to what a dashboard author can already do, but it is the one trust-boundary consideration in this diff and it is cheap to bound.

### Empty and invalid patterns are silently persisted

`handleAddColorOverride` pushes `{ regex: '', color: DEFAULT_COLOR_VALUE }`, and both the runtime and the schema accept it, so a user who clicks "Add Color Override" and then saves ships a no-op entry. Every keystroke is persisted (consistent with other editors in the repo), so transiently invalid states like `[` land in the spec, and the field never signals that the pattern will not compile. Compiling in the change handler with `error`/`helperText` on the TextField, plus `strings.MinRunes(1)` on `regex` in CUE, closes both ends.

The `n°` labels follow the convention in `QuerySettingsEditor`, but the color picker's accessible name is derived from the pattern (`change ${override.regex || 'Color override n°N'} color`), so two overrides sharing a pattern produce two identically named buttons (likely; the label flows into `OptionsColorPicker`'s `aria-label`). Including the index unconditionally keeps the names unique.

### Model exports

`DEFAULT_COLOR_OVERRIDES` is exported and never referenced; since `src/index.ts` re-exports `./bar-chart-model`, it lands in the published API surface. `DEFAULT_VISUAL` is a single module-level `{}` referenced from both `createInitialBarChartOptions()` and the reset handler, so all newly created panels alias one object; immer's copy-on-write keeps that safe today, but any direct mutation would leak across panels. Seeding `visual: {}` on create also writes an empty object into every new BarChart spec.

### Test coverage

`getOverrideColor` is covered thoroughly (first match wins, no match, undefined overrides, invalid and empty patterns skipped), the editor tests cover add and remove including the `onChange` payloads, and the new schema fixture runs under `make test-schemas-plugins`.

Not tested: `handleColorOverrideRegexChange` and `handleColorOverrideColorChange`; the reset handler now writing `visual`; that an override actually reaches `series.itemStyle.color` in the grouped path or the per-bar callback in the ungrouped path, which is the part most likely to break on an ECharts upgrade; case sensitivity and unanchored matching, the semantics users hit first; and an invalid schema fixture.

### Validation run

`npm run type-check -w barchart`, `cue fmt --check`, `go build ./...` in `barchart/`, and `go run ./scripts/test-schemas-plugins/test-schemas-plugins.go` (including `bar_color_overrides.json`) all pass. Jest could not run here: `npm run test -w barchart` fails resolving `../jest.shared` from `jest.config.ts` on Node 22.23 (`.nvmrc` pins 22.14), and unrelated workspaces fail identically, so it is environmental rather than PR-related. `barchart` has no e2e coverage, so no Playwright updates are implied.
